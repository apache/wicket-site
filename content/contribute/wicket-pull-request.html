Send a pull request to Wicket

From an issue to a reviewed pull request against apache/wicket, for your first contribution or your fiftieth.

Wicket’s code lives in apache/wicket on GitHub. You change it in your own copy, send the change as a pull request, and a committer, a member of the project who can merge, reviews it. This page takes you through it in order; for a first time, the tutorial Your first pull request goes through the same steps with a real issue. You need a GitHub account, Git, a JDK and Maven; Build and test Wicket says which versions. The rules a contribution follows are in CONTRIBUTING.md in the repository.

1. Pick or open an issue

Every change starts from an issue in the issue tracker. Issues labelled good first issue are small and need little knowledge of Wicket.

Comment on the issue that you are working on it, so that nobody else starts the same change. A claim without a pull request lapses after two weeks; if you need more time, say so on the issue. Ask your questions there as well: what the expected behaviour is, where the code is, how to test it. The people who answer would rather spend five minutes on a question than review a pull request that went the wrong way.

For a bug you found yourself, open an issue first. Say which Wicket version you use, and add a quickstart, a small project that shows the bug. Issues from before 2026 are in the read-only Jira archive; search it too. A security problem never goes into an issue: report it privately.

2. Fork and clone

Fork apache/wicket on GitHub with the Fork button. Clone your fork and add the Wicket repository as upstream:

git clone https://github.com/<your-account>/wicket.git
cd wicket
git remote add upstream https://github.com/apache/wicket.git

3. Create a branch from master

Wicket has a branch for every release line, a major version that still gets releases:

Branch Release line Pull requests
master Wicket 12, not released yet (Jan 2027) Send them here.
wicket-11.x Wicket 11, the current release Committers copy fixes here.
wicket-10.x Wicket 10, long-term support (LTS) Committers copy fixes here.

Start from master, also when you found the bug in an older version. After the merge, the committers copy the fix to the older branches where it applies; this is called cherry-picking. Say in the issue which versions the bug affects. Why fixes go to master first explains the reasons. Branches of versions that no longer get releases are under archive/.

Give your branch a name that says what it does:

git fetch upstream
git checkout -b keep-url-fragment upstream/master

4. Build Wicket

Build everything once, without the tests. The first time, this downloads the libraries Wicket uses and takes a few minutes:

mvn install -DskipTests -Pfast

It ends with BUILD SUCCESS. Build and test Wicket explains the options and what to do when the build fails. To work in IntelliJ IDEA, Eclipse or NetBeans, see Set up your IDE.

5. Change the code and add a test

Make the change, and add a test that fails without it and passes with it. A bug fix without a test is rarely merged.

The test is often in a different module than the code. The tests for wicket-core, for example, are in wicket-core-tests. Find the existing test of a class by its name plus Test:

git ls-files "*/UrlRendererTest.java"

Run the test with Maven. Because the test is in another module, Maven uses the module you changed from your local Maven repository, so install the changed module first:

mvn install -DskipTests -Pfast -pl wicket-request
mvn verify -pl wicket-core-tests -Dtest=UrlRendererTest

Repeat both commands after every change. Without the first one, the test runs against your previous build and passes or fails for the wrong reason. Run one test has the details, and Run the JavaScript tests covers changes to .js files.

Follow the code conventions: the code format of the file you edit, the license header on every new file, @since on new public methods and classes, and a test class name that ends in Test.

6. Run the full build

Before you send the pull request, build and test everything the way GitHub does it for every pull request:

mvn clean verify -Pjs-test

This runs all tests, the JavaScript tests and the license header check, and takes longer: on a laptop, count on a quarter of an hour or more. It has to end with BUILD SUCCESS.

7. Commit

Commit your change with a message in this form:

Keep the fragment in UrlRenderer.renderFullUrl

renderRelativeUrl kept the fragment of a URL, but renderFullUrl dropped
it, so a full URL to a page section pointed to the top of the page.
renderFullUrl now appends the fragment in the same way.

GitHub issue #<number>

The first line says what the change does, in a normal sentence, without the issue number or a prefix like fix:. After an empty line, the body says what was wrong, why, and what is different now. The last line refers to the issue. For an issue that came from Jira, keep its key, such as WICKET-7165, in the body.

If you used a generative AI tool to write the change, say so in a last line such as Generated-by: <name of tool> <version>, as the ASF recommends. You stay responsible for every line of it.

Check which files you changed, add them, and commit:

git status
git add wicket-request/src/main/java/org/apache/wicket/request/UrlRenderer.java
git add wicket-core-tests/src/test/java/org/apache/wicket/core/request/cycle/UrlRendererTest.java
git commit

git commit opens a text editor for the message. If it opens one you do not know, set your own with git config --global core.editor, or commit from the commit window of your IDE.

8. Open the pull request

Push the branch to your fork:

git push -u origin keep-url-fragment

GitHub does not accept your password here. Sign in with the GitHub CLI or a personal access token, or clone over SSH.

GitHub then shows a button to compare and open a pull request. Check that the base repository is apache/wicket and the base branch is master. Give the pull request the first line of your commit message as title, and in the description say what changed, how you tested it, and Fixes #<number> for the issue. If the work is not finished but you want early feedback, open it as a draft.

GitHub runs the same full build on several JDKs; the result shows at the bottom of the pull request. On your first pull request, a committer may have to approve that run before it starts.

9. Work with the review

A reviewer comments on the pull request. Committers are volunteers, so a review can take a few days. If nothing happens for a week, ask for a review in a comment or on the developers list.

To answer a review, commit the changes on the same branch and push again; the pull request updates itself. Separate commits for review comments are fine while the review lasts, so that the reviewer sees what changed. They do not stay: before the merge, each is squashed into the commit it belongs to, so that master gets no “review comments” commits. The committer who merges tells you whether to do that yourself or whether they squash when merging.

To squash yourself, start an interactive rebase, mark each review commit as fixup and move it below the commit it belongs to, and force-push your branch:

git fetch upstream
git rebase -i upstream/master
git push --force-with-lease --force-if-includes origin keep-url-fragment

Force-pushing is fine for your own pull request branch; only the branches of apache/wicket refuse it. --force-with-lease --force-if-includes refuses to overwrite commits on your fork that you have not seen, for example ones you pushed from another computer.

When the committer asks you to bring the branch up to date with master, rebase it or merge master into it, whichever they ask for. To rebase:

git fetch upstream
git rebase upstream/master
git push --force-with-lease --force-if-includes origin keep-url-fragment

To merge:

git fetch upstream
git merge upstream/master
git push

A committer merges the pull request when it is ready. The change goes out with the next Wicket 12 release, and with the next release of every older line it was copied to.

Ask questions

Ask in the issue you work on, in GitHub Discussions, or on the developers list, dev@wicket.apache.org. Questions about building Wicket, finding code or writing a test are normal there. To write to the list, subscribe first by sending a mail to dev-subscribe@wicket.apache.org; the archive shows earlier conversations.
